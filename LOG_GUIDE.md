# Understanding Your p2pool-go-VTC Logs

This guide explains the console and `p2pool.log` messages generated by `p2pool-go-VTC` to help you monitor node health, share validation, consensus verification, and block discovery.

---

## Log Levels, Thresholds & Color Scheme

The `logging` package (`logging/log.go`) formats all messages with microsecond timestamps (`YYYY/MM/DD HH:MM:SS.ffffff`) and ANSI color codes, writing simultaneously to your terminal (`stdout`) and `p2pool.log`.

| Prefix | ANSI Color | Config Level Threshold | Purpose |
| :--- | :--- | :--- | :--- |
| **`[ERROR]`** | Red (`\033[31m`) | `error` (`0`) | Critical failures requiring attention (RPC errors, invalid configuration, consensus rejections). |
| **`[WARN]`** | Yellow (`\033[33m`) | `warn` (`1`) | Non-critical issues (stale/DOA shares, orphaned blocks, unreachable bootstrap peers). |
| **`[INFO]`** | Bright White (`\033[97m`) | `info` (`2`) | Standard operational events (new block templates, miner connections, 30-second status summaries). |
| **`[SUCCESS]`** | Green (`\033[32m`) | `info` (`2`) | Key milestones (accepted shares, BIP22 consensus verification, LAN peer discovery, solved blocks). |
| **`[NOTICE]`** | Magenta (`\033[35m`) | `info` (`2`) | Noteworthy state changes. |
| **`[DEBUG]`** | Cyan (`\033[36m`) | `debug` (`3`) | Verbose protocol tracing (raw Stratum JSON traffic and individual Verthash header evaluations). |

> **Note:** Because `[SUCCESS]` and `[NOTICE]` are gated at the `info` threshold (`LogLevelInfo = 2`), setting your log level to `"info"` is recommended for normal operation so share acceptances and block discoveries are always displayed.

---

## Setting the Log Level

1. **In `config.yaml`**:
   ```yaml
   loglevel: "info" # Options: "error", "warn", "info", "debug"
   ```

2. **Via Command-Line Flag** (overrides `config.yaml`):
   ```bash
   ./p2pool-go-vtc -loglevel debug
   ```

---

## Viewing `p2pool.log` with Colors

Because `logging.SetLogFile` writes the same ANSI-colored stream to both the console and `p2pool.log`, use `less -R` or `tail` when inspecting the log file so your terminal renders the color codes cleanly instead of showing raw `\033[...` sequences:

```bash
# Follow live logs with full color rendering
tail -f p2pool.log

# Scroll through historical logs with color support
less -R p2pool.log
```

## Key Log Messages

### Startup & Shutdown (`main.go` & `verthash/`)

- `[INFO] 🚀  p2pool-go (GossipSub mesh) starting up`
  * The node is initializing.
- `[INFO] Verthash: Verthasher initialized successfully (verthash.dat: ..., keepInRam: true)`
  * `verthash.dat` has been loaded into RAM for sub-millisecond share PoW verification.
- `[INFO] Loaded 859 shares from disk`
  * The verified shares in `sharechain.db` were loaded into `ShareChain` memory on startup. On the first start after upgrading, a `[INFO] Migrated N shares from sharechain.json to sharechain.db` line precedes it.
- `[INFO] MAIN: Startup complete – Stratum + Web UI on :9172. Press Ctrl+C to exit.`
  * The `cmux` listener is live and serving both Stratum miners and the HTTP Web UI on port `9172`.
- `[WARN] Shutdown signal received. Saving share chain and exiting…` / `[INFO] Sharechain committed successfully.`
  * The node caught `Ctrl+C` or `SIGTERM` and safely wrote the shares verified or pruned since the last save to `sharechain.db`.

### P2P Networking & Light Mode (`p2p/`)

- `[INFO] Running in daemon-less LIGHT MODE (receiving block templates via P2P)`
  * Node started with `-light` and is receiving `BlockTemplate` updates from full-node peers.

- `[INFO] P2P Node started! Persistent Peer ID: 12D3KooW...`
  * `go-libp2p` initialized using the persistent key in `peer.key`.
- `[INFO] P2P Connect Multiaddr: /ip4/192.168.0.140/tcp/9348/p2p/12D3KooW...`
  * The exact multiaddr other `p2pool-go-VTC` nodes can add to their `config.yaml` (`peers:`) to connect to your node.
- `[SUCCESS] P2P mDNS: Connected to local LAN peer 12D3KooW...!`
  * Another `p2pool-go-VTC` node on your local network was automatically discovered and connected via mDNS.
- `[INFO] P2P: Validated and added remote peer share ... to ShareChain`
  * A share broadcast by a remote peer over GossipSub passed Verthash PoW validation and was added to your PPLNS window.

### Stratum, Consensus & Block Finding (`stratum/` & `work/`)

- `[INFO] Stratum: New miner connection from 192.168.0.141:31773` / `[INFO] Stratum: Miner authorizing address: 'vtc1q...'`
  * A miner connected and authorized with a valid Vertcoin Bech32 or Base58 payout address.
- `[SUCCESS] SHARE ACCEPTED from vtc1q... (Share Diff: 0.76671 / Target Diff: 0.16000)`
  * The miner's submission passed Verthash PoW validation and met its current Vardiff target.
- `[SUCCESS] CONSENSUS VERIFIED: vertcoind validated full candidate block for height 2699826 (Coinbase, PPLNS Outputs, SegWit Commitment & Merkle Root 100% valid!)`
  * Triggered on the first valid share of each new block height. Confirms that `vertcoind` ran `TestBlockValidity()` on your node's complete candidate block and verified that all consensus rules and PPLNS coinbase outputs are 100% valid.
- `[SUCCESS] !!!! BLOCK FOUND !!!! Share meets network target! Submitting to vertcoind...`
  * A miner's share difficulty met or exceeded the full Vertcoin network difficulty target.
- `[SUCCESS] SUCCESS! Block ... (Height 2699864) ACCEPTED by the Vertcoin network!`
  * `vertcoind` accepted the solved block via `submitblock` and broadcast it to the Vertcoin blockchain, minting the PPLNS outputs directly to the miners' wallets in the coinbase transaction.
- `[SUCCESS] Block ... is now MATURE (100 confirmations)! Direct coinbase PPLNS outputs are now spendable.`
  * The solved block reached 100 confirmations on the Vertcoin network.
